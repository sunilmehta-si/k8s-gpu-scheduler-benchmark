# Changelog

## [Unreleased]

### Fixed
- The README's real-scheduler table put Kueue as installed at $3.97 per useful GPU-hour, level with KAI. That came
  from one run (38889757797), and it was Kueue's less common outcome. Over all 30 runs since the kwok fixes, Kueue
  as installed costs $5.21 in 21 runs and $3.98 in 9, and the default scheduler and Volcano split the same way.
  Whether an inference pod lands on an H100 node decides every default-scheduler and Kueue run. The table now shows
  medians over every run and each outcome's cost; the stacks that score GPUs give one outcome each, within 4%.
  `results/cluster/` now holds run 43266087495 (current pins), which shows each stack's usual outcome.

### Added
- `gsb repeats` summarises many cluster runs: each stack's median and range, its outcomes when its costs split, and
  per run the metrics, the nodes each job kind used and when each job started. `scripts/fetch-cluster-runs.sh`
  downloads every successful run on `main`; `results/cluster/repeats.json` and `repeats.md` keep the 30 runs from
  16 October to 12 November, since GitHub deletes the artifacts after 90 days. Tests hold the README table and what
  the README and docs say about each outcome to the committed runs.
- `docs/cluster-runs.md` explains why one run is one draw, and lists a kwok gap: it completes a pod on schedule even
  when the rest of its gang never started, so the expensive outcome is if anything cheaper here than on real GPUs.
- Dependabot updates wait 14 days after a release, like the pins `gsb versions` checks, and `tests/test_dependabot.py`
  holds the cooldown.
- `gsb versions` checks that the pinned kind node image, digest and all, is one the pinned kind release's notes list,
  and exits 1 when it is not; the report also lists the pins it does not compare, with the reason, and a test holds
  every line of `cluster/versions.env` to one list or the other.
- `gsb versions --json` carries the node-image check as a final object beside the drift rows.
- `gsb versions` names an earlier release that is already 14 days old when the newest is not (Kueue v0.20.4
  while v0.20.5 waits), and `--strict` fails on it. Before, such a pin read as "too new" until the newest release
  aged, holding back a fix that was ready. `--json` adds `adoptable_now`, `ready` and `ready_published`.

### Changed
- The cluster workflow installs Kueue v0.20.4 (was v0.20.3; published 29 Oct, adoptable from 12 Nov). Its notes
  change Kueue's scheduler log messages and levels; the runs collect those logs but nothing here parses them.
- Pull requests are reviewed with the code review tool at v0.9.0.
- `gsb versions` reports the newest stable release (the highest plain x.y.z that is not a draft or prerelease), not
  the one GitHub marks latest, so a project that marks its release candidates is not compared against one.

### Added
- CI runs weekly as well as on every push, so the pin drift report in the summary stays current between pushes.
- `docs/cluster-runs.md` says how to bump a pinned release and what to look at in the cluster run that follows.

## [0.5.0] - 2026-10-29

### Added
- `gsb versions`: each pin in `cluster/versions.env` against its latest upstream release, how far behind it is, and
  when a newer release becomes adoptable (14 days after publication); `--strict` fails only on adoptable ones. CI
  writes the table into every run's summary without failing the build. `--json PATH` writes the rows with their
  dates, and `make versions` runs the report.
- A `code-review` workflow: every pull request is reviewed by agentic-code-review-tool v0.7.0 on its changed lines.

### Changed
- Every cluster component is pinned in `cluster/versions.env`: kind, the Kubernetes node image by digest, kwok and
  the three schedulers. The install scripts read it, and a variable set in the environment still wins.
- The cluster workflow gives kind-action the pinned kind release and node image. Before, the action's own defaults
  chose the Kubernetes version, so upgrading the action could have changed the cluster under the results.

## [0.4.0] - 2026-10-25

### Added
- A 1,024-GPU data-centre fleet (`fleets/dc-1024.yaml`: the mixed-256 node mix at four times the size), a 611-job
  8-hour trace for it, and its committed results, report and chart, regenerated by `make results` and checked by
  the tests like the other two fleets. At that scale every stack finishes the trace at the same cost per useful
  GPU-hour; they differ in queue wait, stranded GPU-hours and fragmentation.

### Changed
- The cluster workflow installs KAI Scheduler 0.18.6 (was 0.18.5).
- The cluster workflow installs Kueue v0.20.3 (was v0.20.1).

## [0.3.0] - 2026-10-16

### Added
- Tuned variants `default-binpack`, `kueue-binpack` and `volcano-binpack`: the same stacks configured to bin-pack GPUs.
  `gsb manifests --part scheduler` renders their configuration (a second kube-scheduler with a `MostAllocated`
  profile on `nvidia.com/gpu`; Volcano's scheduler ConfigMap with `binpack.resources`), with install scripts and runs
  in the cluster workflow for all seven stacks.
- Placements: cluster runs record where and when every pod ran, `gsb simulate --placements` does the same for the
  model, `gsb timeline` lists them per node, and `gsb compare` adds a per-job table of start times and GPU pools.
- Placement models `random` (seeded; what a scheduler does when its scoring ignores GPUs) and `most-pods`, and
  Volcano's 1.2x overcommit enqueue gate.
- A start-lag check in cluster runs: pods must start within 2 s of being bound, or `--strict` fails the run.
- The cluster workflow keeps pod objects, events and scheduler logs, and posts the comparison and timelines.
- docs/gpu-scoring.md: which schedulers bin-pack GPUs out of the box, why, and the setting that fixes each.
- A ten-trace sweep of all seven stacks (`results/sweep-mixed-256-tuned.md`).

### Changed
- Presets follow what the schedulers actually do with GPU-only pods: default and Kueue place at random among
  feasible nodes (kube-scheduler scores only cpu and memory), Volcano places by pod count (its binpack packs the
  default cpu request) behind the overcommit gate. KAI still bin-packs GPUs.
- The headline: out of the box only KAI bin-packs GPUs. On the real schedulers, configuring it cut Volcano's time to
  finish and cost per useful GPU-hour by 26% and the default scheduler's cost by 20% on the smoke trace; in
  simulation the saving holds for every stack over ten traces. This replaces 0.2.0's "bin-packing stacks are about
  19% cheaper", which compared against a default scheduler that spread GPU pods, which it does not do.
- The model is within 4% of real Volcano (median over 100 placement seeds) and 6% of every GPU-packing stack.
- Sweeps seed placement with the trace seed; the ablation starts from random placement and adds a GPU-spread step.

### Fixed
- kwok's pod-create and pod-ready stages kept their default 1-6 s delays, which idled every bound pod's GPUs for a
  median 30 trace minutes at 300x on every stack. Both are now 0 s.
- Preempting a job whose replicas had partly finished returned the finished replicas' GPUs, quota and cost again.
- `make cluster`'s STACK value no longer carries trailing spaces from a comment.

## [0.2.0] - 2026-10-15

### Added
- Real-scheduler runs: `gsb cluster run` creates kwok GPU nodes, applies a stack's queues, replays a trace at a
  chosen speed, and collects pod placement and timing into the same results schema (`"mode": "cluster"`).
  `gsb compare` puts a cluster run next to the model.
- A `cluster` workflow that runs the default scheduler, Kueue v0.20.1, Volcano v1.16.0 and KAI Scheduler 0.18.5 on
  kind + kwok v0.8.0 on every push, with install scripts and a self-check that fails runs whose pods did not run
  for their expected time. The first runs and comparisons are committed under `results/cluster/`.
- `gsb sweep` (mean, spread and range over seeded traces, plus cheapest-stack wins), load curves with `--rates`,
  and `gsb ablate`, which switches behaviours on one at a time.
- `gsb chart`: accessible, theme-aware SVG bar charts.
- Priority preemption in the model (cluster-wide for the default scheduler, within a team for Kueue and KAI), and
  jobs that require a GPU model (`gpu_model` in traces, `--pin-training` in the generator).
- A 10-seed sweep of the 256-GPU fleet, charts, a Makefile, a contributing guide and docs/cluster-runs.md.

### Changed
- The README's headline finding: bin-packing, not gang scheduling, drives the savings, and the advantage is about
  19% over ten traces rather than one trace's 23%.
- With priority preemption modelled, the default scheduler no longer finishes the 32-GPU lab trace first.

### Fixed
- kwok's jitter delay is an upper bound, so the `0s` value completed every fake pod instantly; it now equals the
  delay. The runtime check caught this in CI.

## [0.1.0] - 2026-10-14

### Added
- Fleets of GPU node pools (prices, labels, taints) and their rendering as kwok fake nodes.
- JSONL workload traces and a seeded generator with a training, fine-tune, inference and notebook mix; two sample traces.
- A discrete-event reference simulator: pod-by-pod or gang placement, spread or bin-packing, strict or best-effort
  queueing, team quotas with borrowing and reclaim, checkpoint-aware preemption, stranded-GPU and deadlock detection.
- Presets that model the default kube-scheduler, Kueue, Volcano and KAI Scheduler.
- Metrics: utilisation and useful utilisation, makespan, queue-wait percentiles, stranded and preempted GPU-hours,
  fragmentation, fairness between teams, and cost per team, model and useful GPU-hour.
- `gsb simulate` (deterministic results JSON) and `gsb report` (Markdown comparison).
- `gsb manifests` for the default scheduler, Kueue, Volcano and KAI Scheduler, against kwok nodes.
- Committed results for both sample fleets, checked in CI.
